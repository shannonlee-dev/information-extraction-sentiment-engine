## 2. 분석 방식

### 정보 추출

- 이메일
- 전화번호
- 날짜
- 금액
- URL

공통 흐름은 다음과 같다.

```text

→ 정규화
→ 결과 반환
```

```yaml

```

정규식만 사용하지 않고 날짜 유효성, 전화번호 형식, URL host, 금액 단위 순서 등을 추가로 검사한다.

## 3. 감성 분석 방식

감성 분석은 단순히 문장에 특정 단어가 포함되어 있는지만 보는 방식이 아니다.

전체 흐름은 다음과 같다.

```text
입력 문장
→ KOMORAN 형태소·품사 분석
→ 감성 사전과 형태소 sequence 매칭
→ 감성 event 생성
→ 주변 부정어/강조어 규칙 연결
→ 각 event의 점수 계산
→ 모든 점수 합산
→ positive / negative / neutral 판정
```

### 3.1 형태소 분석

한국어는 활용형이 많기 때문에 표면 문자열만 비교하면 같은 의미의 표현을 놓치기 쉽다.

```text
좋다
좋아요
좋았어요
좋습니다
```

따라서 KOMORAN으로 문장을 형태소와 품사 단위로 분석한다. 감성 사전도 단순 문자열이 아니라 `(형태소, 품사)` 조합으로 컴파일되어 있어 실제 활용형을 분석한 결과와 비교한다.

### 3.2 감성 사전

최종 compiled 사전은 다음과 같다.

- canonical entry: **565개**
- 긍정: **207개**
- 부정: **358개**
- 점수 범위: `-3 ~ -1`, `+1 ~ +3`

예를 들면 다음과 같다.

```text
좋다    +2
최고    +3
만족    +2

나쁘다  -2
불만    -2
최악    -3
```

점수는 머신러닝이 학습한 확률이 아니라 사람이 정한 규칙 기반 강도다.

### 3.3 감성 표현 매칭

형태소 분석 결과를 감성 사전과 비교해 감성 표현을 찾는다. 같은 위치에서 여러 표현이 겹치면 대체로 다음 순서로 하나의 감성 event를 선택한다.

```text
왼쪽부터 탐색
→ 더 긴 표현 우선
→ priority가 높은 항목 우선
```

### 3.4 강조어

`정말 좋다`, `매우 만족하다`처럼 강조어가 감성 표현에 연결되면 감성 점수에 배수를 곱한다. 여러 강조어가 겹치더라도 최종 강조 배수는 최대 `2.0`으로 제한한다.

### 3.5 부정어

대표적으로 다음 구조를 처리한다.

```text
안 좋다
못 만족하다
좋지 않다
만족하지 못하다
만족이 없다
```

부정이 한 번 연결되면 점수의 부호가 반전된다.

```text
+2 → -2
```

이중부정은 부정 횟수가 2회가 되므로 다시 원래 부호로 돌아간다.

```text
+2 × (-1)^2 = +2
```

### 3.6 최종 점수

각 감성 event의 contribution은 다음과 같이 계산한다.

```text
기여도 = 기본 감성 점수 × 강조 배수 × (-1)^(부정 횟수)
```

문장 전체 점수는 모든 기여도의 합이다.

```text
score > 0 → positive
score < 0 → negative
score = 0 → neutral
```

예를 들어 `정말 좋지 않다`는 다음과 같다.

```text
좋다  +2
정말  ×1.5
않다  ×-1

최종 = -3
→ negative
```

## 4. 평가 방식

### 정보 추출

50개 이상의 고정 테스트 문장으로 평가한다. 예측이 정답과 다음 항목까지 모두 일치해야 TP로 인정한다.

- 정보 유형
- 원문 위치
- 정규화 값

Precision, Recall, F1을 계산한다.

### 감성 분석

100개 이상의 positive/negative 고정 데이터를 사용한다. 같은 데이터에서 modifier OFF와 modifier ON을 비교하여 부정어·강조어 규칙의 효과를 확인한다. Accuracy와 Macro F1을 계산한다.

## 5. 외부 final 10,000건 데이터

고정 fixture만 잘 맞춘다고 해서 실제 사용자 문장에서도 잘 작동한다고 볼 수는 없다. 그래서 별도의 외부 쇼핑 리뷰 데이터로 최종 일반화 성능을 평가했다.

외부 일반화 성능 평가는 [네이버 쇼핑 리뷰 감성 말뭉치 (bab2min/corpus)](https://github.com/bab2min/corpus)를 사용했다. 원본 데이터에서 개발 중 노출된 문장 및 중복·유사 문장을 분리한 뒤, 독립 holdout 10,000건을 final 평가 데이터로 사용했다.

프로젝트 기록상 원본 파일은 `naver_shopping.txt`다. 최종 10,000건은 테스트 코드 안에서 임의로 만든 문장이 아니라 네이버 쇼핑 리뷰 기반 외부 데이터에서 분리한 holdout이다.

### 5.1 데이터 분리 방식

개발 중 이미 본 문장과 너무 비슷한 리뷰가 final에 들어가면 성능이 부풀려질 수 있다. 그래서 final을 만들기 전에 기존 개발 데이터, 테스트 fixture, 문서 예문, 수동으로 사용한 예문 등 이미 노출된 문장을 등록했다.

그 뒤 원본 리뷰들과 비교해 다음 항목을 확인했다.

- 정규화 후 완전 중복
- 길이 20자 이상 문장에 대한 5-shingle Jaccard 유사도 `>= 0.85`
- 기존 개발 데이터와 연결되는 near-duplicate

비슷한 문장이 여러 개 있으면 서로 다른 split으로 흩어지지 않도록 그룹 단위로 분리했다.

### 5.2 최종 split

분리 결과는 다음과 같다.

```yaml
selection: 5,000건
final: 10,000건
future reserve: 126,888건
```

최종 후보가 이미 하나로 정해져 있었기 때문에 selection 5,000건은 파일만 준비하고 실제 후보 선택에는 사용하지 않았다. 최종 평가는 final 10,000건에 대해 한 번만 실행했다. final 데이터는 9,999개의 그룹으로 구성되었다.

### 5.3 일회성 평가 원칙

final 결과를 보고 다시 규칙이나 사전을 수정한 뒤 같은 데이터로 평가하면 그 데이터는 더 이상 독립적인 final이 아니다. 다음 순서로 진행했다.

```text
후보 M2-L 동결
→ final 10,000건 1회 평가
→ 결과 기록
→ 동일 final 재평가 금지
```
