# 미션 범위 내 감성 분석 재설계 Implementation Plan

> **For agentic workers:** 실행 지시를 받은 뒤 `superpowers:executing-plans`로 아래 작업을 순서대로 진행한다. 체크박스는 실행 결과가 확인됐을 때만 표시한다. 현재 사용자의 요청은 **계획 작성 후 대기**다.

**Goal:** 표현별 정답 암기를 제거하고, 재현 가능한 언어 처리와 독립 평가로 성능의 범위 및 불확실성을 설명할 수 있는 사전·규칙 기반 감성 엔진을 만든다.

**Architecture:** KoNLPy/KOMORAN으로 형태소·품사·원문 위치를 얻고, 같은 표현 체계로 정규화한 감성 사전을 매칭한다. 부정·강조는 제한된 구문 구조에 연결하여 점수를 합성한다. 개발 데이터와 최종 평가 데이터의 접근 및 사용 목적을 분리한다.

**Tech Stack:** Python 3.10+, 내장 `re`, KoNLPy/KOMORAN, JPype/JVM, pytest. 형태소 분석은 기존 분석기를 사용하며 감성 판정은 사전과 명시적 규칙으로 수행한다. 실행 환경 검증 전에는 새 의존성이 동작한다고 주장하지 않는다.

**Spec:** `docs/private/mission.md`, `docs/private/rubric.md`, 본 문서의 설계·평가 계약. 2026-09-04 설계의 자체 제약인 “KoNLPy 추가 금지”는 미션 요구가 아니므로 이 계획에서 대체한다. 미션 원문은 수정하거나 공개 문서에 전문 복제하지 않는다.

**상태:** 계획만 작성. 기존 소스·사전·평가 데이터 변경, 패키지 설치, 데이터 다운로드, 학습·성능 실험, 커밋은 이 단계에서 실행하지 않는다.

## 1. 성공의 정의와 고정 제약

| 미션 요구 | 구현·검증 계약 |
|---|---|
| Python 3.10 이상 | Python 3.10 및 현재 개발 환경에서 관련 테스트·설치 검증 |
| 내장 `re` 기반 5종 정보 추출 | 이메일·전화·날짜·금액·URL, 유형별 3종 이상 변형과 정규화 유지 |
| 감성 사전 200개 이상 | 활용형 중복을 제외한 의미 항목 200개 이상, 도메인 항목 직접 작성 30개 이상 |
| 토큰화·사전 점수 합산 | 형태소·품사 기반 매칭, 설명 가능한 개별 기여도와 합계 |
| 부정·강조·이중부정 | 단일부정, 강조 배수, 명시된 이중부정 구성의 실제 연결 및 계산 검증 |
| 추출 평가 50문장 이상 | 유형별 10문장 이상, Precision/Recall, 실패 5건 이상 분석 |
| 감성 평가 100문장 이상 | Accuracy/F1, 수정어 전후 비교, 실제 오분류 10건 이상 분석 |
| 설치·실행·유지보수 설명 | 의존성·자원 버전, 실행 명령, 규칙 근거·충돌·한계 기록 |
| 반어·Aspect·문맥 | 선택 범위다. 미지원 사례를 평가에서 삭제하거나 억지 정답 규칙으로 보정하지 않는다 |

공개 `analyze_sentiment(text, apply_modifiers=True)`와 통합 `analyze`의 호출 형태, `SentimentResult`/`SentimentMatch`의 기존 필드는 유지한다. `tokens`는 기존 원문 토큰 표시를 유지하고 내부 형태소 표현을 별도로 둔다. 정보 추출의 동작을 이번 감성 재설계와 함께 변경하지 않는다.

### 두 개의 완료 기준

1. **구현 완료:** 미션 기능, 규칙의 계약, 원문 위치·점수 근거, 재현 가능한 설치와 회귀 검증을 충족한다.
2. **성능 목표 달성:** 개발에 노출되지 않은 최종 데이터에서 아래 사전 등록 기준을 통과한다.

첫 번째만 충족하면 “구현 완료, 일반화 성능 미검증/목표 미달”로 보고한다. 테스트 통과 수와 합성 문장 정확도를 두 번째 기준의 근거로 대체하지 않는다.

## 2. 현재 결과의 올바른 위치

이 절은 앞선 실행에서 얻은 관측 기록이며 이번 계획 작성 중 다시 실행한 결과가 아니다.

| 실험 | 기존 합성 100문항 | 추가 합성 100문항 | 해석 |
|---|---:|---:|---|
| 원래 구현 | 44% | 7% | 활용형 인식·규칙 구현의 결함을 포함한 기준선 |
| 새 규칙 + 기존 감성 사전 | 81% | 90% | 공통 규칙 개선 효과가 있다는 개발 데이터상의 근거 |
| 현재 구현에서 해결 구문 4개 제외 | 91% | 90% | 특정 구문 추가가 기존 평가 1건을 개선 |
| 현재 작업 트리 전체 | 92% | 90% | 개발에 노출된 합성 데이터 결과, 독립 평가 아님 |

`tests/fixtures/sentiment_cases.json`과 `sentiment_validation_cases.json`은 모두 **개발·회귀 데이터**로 재분류한다. 추가 데이터가 구현 전에 고정되었다는 사실만으로 평가 독립성이 생기지 않는다. 앞으로 이 문장들을 다른 파일로 옮기거나 다시 분할해 보류 데이터라고 부르지 않는다.

현재 작업 트리의 변경 사항은 미커밋 상태다. 실행 시작 시 HEAD만 기록하면 현재 구현을 재현할 수 없으므로 추적 파일 diff와 미추적 파일도 함께 보존한다.

## 3. 선택한 설계와 제외한 접근

| 접근 | 판단 |
|---|---|
| 자체 어미 생성기·예외 구문을 계속 증설 | 채택하지 않음. 언어 분석과 감성 판단이 섞이고 관측한 표현에 의존하기 쉽다 |
| 기존 형태소 분석기 + 출처 있는 사전 + 범위가 명확한 감성 합성 | **채택.** 한국어 활용 처리와 감성 규칙을 분리하고 각각 검증할 수 있다 |
| 학습된 문장 감성 분류기로 대체 | 이번 기본 구현에서 제외. 미션의 사전·규칙 계산 요구를 우회하지 않는다 |

형태소 분석기 사용은 감성 성능의 보증이 아니다. 형태소 오분석, 사전 의미 충돌, 부정 범위 오류를 구분해서 관찰할 수 있는 구조를 선택한 것이다.

### 처리 흐름

```text
입력 원문 ─────────────────────────────────────→ 기존 정보 추출
   │
   └→ 형태소·품사·위치 → 감성 사전 매칭 → 국소 구문 구성
                                             │
                                             └→ 부정·강조 적용 → 점수 합산
                                                               │
                                      원문 범위·개별 기여도 ←────┘
```

### 형태소와 원문 위치

- `src/sentiment_engine/korean.py`를 어미 생성기가 아닌 하나의 KOMORAN 어댑터로 교체한다. 분석기 선택 레지스트리나 여러 백엔드 프레임워크를 만들지 않는다.
- 입력과 사전을 같은 분석기·모델·설정으로 분석한다. 어간만 비교하지 않고 품사와 파생 접사를 포함한 어휘 단위를 사용한다.
- KoNLPy의 `Komoran.pos()`가 제공하는 형태소·품사 쌍만으로 원문 위치를 추정하지 않는다. 확인한 wrapper 소스는 `flatten=False`에서도 줄 단위 결과를 묶으므로 어절과 `zip`하는 구현을 금지한다. [KoNLPy wrapper 소스](https://github.com/konlpy/konlpy/blob/master/konlpy/tag/_komoran.py)
- 어댑터 내부 한 곳에서 KoNLPy가 초기화한 KOMORAN의 `getTokenList()`를 사용한다. 토큰의 형태소·품사·시작/끝 위치를 읽고, Java UTF-16 위치를 Python 문자열 인덱스로 변환한다. 이 연결은 wrapper 내부 객체에 의존하므로 버전 고정과 실제 API 계약 테스트가 선행 조건이다. [KOMORAN 토큰 API](https://docs.komoran.kr/api/kr/co/shineware/nlp/komoran/model/KomoranResult.html)
- 줄바꿈을 나누어 처리한다면 각 줄의 원문 기준 시작 위치를 더한다. NFC 정규화나 공백 축약을 원문에 적용하지 않는다. 축약형의 여러 형태소가 같은 음절 범위를 공유할 수 있으므로 내부 형태소의 구간 비중첩을 억지로 요구하지 않는다.
- 필요한 위치 API가 제공되지 않거나 원문 정렬 계약이 깨지면 어댑터 오류로 처리한다. `find()`로 대충 위치를 맞추거나 예전 생성기로 조용히 복귀하지 않는다. 평가에서는 오류 건수를 분모에 포함한다.

### 사전과 규칙의 경계

- 사전에는 **의미 항목**을 넣는다. 독립적인 출처가 있는 단어·관용구는 허용하지만, 평가에서 틀린 문장 자체나 조사만 바꾼 같은 구문의 열거는 허용하지 않는다.
- 미션이 제시한 KNU 사전을 기본 확장 자료로 검토한다. 원본 출처·리비전·파일 해시를 고정하고, 감성 0인 항목은 감성 점수 합산에서 제외한다. 원본 점수를 임의의 함수로 과장하지 않는다. [KNU 원본 설명](https://github.com/park1200656/KnuSentiLex)
- 부정·강조가 합성적으로 포함된 표현은 연산자로 처리한다. 비합성 관용구를 원자적 사전 항목으로 유지할 때만 내부 수정어를 이미 소비했다고 표시한다. 전체 KNU 표현을 무검토로 긍부정 문장 lookup으로 가져오지 않는다.
- 정규화 뒤 같은 의미 키에 상충하는 점수가 생기면 충돌 목록에 남긴다. 검토된 도메인 override만 우선하며, 그 외에는 제외한다. 파일 순서에 따른 우선순위나 임의 평균을 쓰지 않는다.
- `문제가 해결되다` 등 이번에 추가한 구문 4개는 제거한다. `문제→해결`처럼 사건의 상태 변화가 개발 자료에서 반복적인 오류 유형으로 확인되면, **사건 종류와 상태 변화 연산자의 조합 규칙**을 별도로 검토한다. 해당 평가 한 건의 점수를 되찾기 위해 이 기능을 의무 구현하지 않는다.

## 4. 수학적 계약: 증명할 것과 측정할 것

감성 사건 집합을 E(x), 사건 e의 사전 점수를 w(e), 구문 구조상 e에 연결된 부정 연산자 집합을 N(e), 강조 배수를 A(e)라 둔다.

```text
A(e) = min(2, ∏ 연결된 강조어 배수)      # 빈 곱은 1
c(e) = w(e) × A(e) × (-1)^|N(e)|
S(x) = round(Σ[e∈E(x)] c(e), 6)
label(x) = positive if S(x)>0; negative if S(x)<0; neutral otherwise
```

홀짝 계산은 **N(e)의 연결이 옳다는 조건 아래** 적용되는 규칙이다. 문장에 등장한 모든 부정어의 수를 세어 복잡한 부정의 의미를 해결했다고 주장하지 않는다.

| 성질 | 검증 방법 및 적용 조건 |
|---|---|
| 근거 보존 | 모든 공개 match에 `text[start:end] == raw` |
| 점수 보존 | `result.score == round(sum(m.contribution), 6)` |
| 소유권 | 같은 어휘 사건을 중복 합산하지 않으며, 단항 수정어는 한 사건에만 연결 |
| 부정 반전 | 지원 문법에서 사건에 연결한 부정 하나는 기여도의 부호 반전 |
| 이중부정 | 동일 사건에 중첩 연결된 두 부정은 원래 부호로 복귀 |
| 강조 | 동일 사건에서 배수는 크기만 바꾸며 부호·연결 대상을 바꾸지 않음 |
| 절 분리 | 별도 절에 추가한 부정어가 기존 절의 사건 기여도를 바꾸지 않음 |
| 원자적 관용구 | 내부 부정 처리와 외부 부정 처리가 각각 정확히 한 번 적용 |
| 결정성 | 같은 코드·사전·모델·설정·입력의 결과가 반복 실행에서 동일 |

위 성질은 구현의 일관성을 검증한다. **자연어 전체에 대한 정확성 정리나 미지 데이터 정확도 보장으로 확장하지 않는다.** 혼합 감성·인용·조건·질문·반어에 관한 미지원 범위도 명세의 일부다.

### 지원할 문법의 초기 범위

1. 감성 용언과 파생 용언: 사전 키 + 품사·파생 접사. 높임·시제·평서 종결 변형은 감성 사건의 동일성을 유지한다.
2. 선행 `안/못`, 후행 `-지 않다/-지 못하다`: 품사와 연결 어미로 해당 술어를 찾는다.
3. 명사 상태의 `없다/아니다`: 감성 명사와 서술어 관계가 국소 구조로 확인되는 경우에만 반전한다. 가까운 임의의 감성어를 반전하지 않는다.
4. `[[감성 술어]-지 않다] + 것은 아니다`: 명사화 범위에 두 번째 부정을 연결한다. 최소 요구 이중부정은 이 구성으로 명확하게 충족한다.
5. 강조 부사 + 감성 사건: 같은 술어 그룹에서만 적용한다. 거리는 안전 상한으로 쓰며 의미 연결의 대용으로 삼지 않는다.
6. 독립 절·대조 절: 사건을 분리해 합산한다. `하지만` 뒤를 무조건 우승시키는 가중치를 추가하지 않는다.

이 밖의 `할 수 없다`, 의향 부정, 상태 변화 등은 개발 데이터의 오류 유형과 독립된 언어적 근거가 함께 있을 때만 확장한다. 자연스러운 문장 하나를 고쳤다는 이유만으로 문법 전체를 지원한다고 쓰지 않는다.

| 외부 쇼핑 후기 최종 분할 | 고정된 후보 1개의 최종 판정 | 결과를 보고 고친 모델을 같은 세트로 다시 합격시키기 |
| 독립 문법·중립 반례 | 지원 문법과 과잉 매칭 검증 | 운영 정확도 추정 |

기본 외부 자료는 `bab2min/corpus`의 네이버 쇼핑 후기다. 원본 설명은 후기와 별점, 1~2점/4~5점의 극성 구분을 제공한다. 이 데이터에서 측정하는 것은 **쇼핑 후기 별점 극성과의 일치도**이며 실제 고객 문의의 감정 정확도와 같다고 부르지 않는다. [말뭉치 원본 설명](https://github.com/bab2min/corpus/tree/master/sentiment)

NSMC는 미션이 제시한 대체 자료지만 영화 도메인이다. 자료 확보 실패 시 몰래 전환하지 않는다. 사용한다면 다른 도메인의 별도 실험으로 등록하고 고객 문의 성능 주장에 사용하지 않는다. [NSMC 원본 설명](https://github.com/e9t/nsmc)

### 분할·접근·누출 방지

- 원본 전체를 프로그램으로 읽어 리비전·SHA-256·필드 정의·레이블 매핑·배포 조건을 기록한다. 모델이 원문을 대량 열람하는 작업과 데이터 준비를 분리한다.
- 원본의 ID가 없으면 파일 해시와 행 번호로 ID를 만든다. **분석 결과나 감성어 유무를 기준으로 샘플을 고르지 않는다.**
- 공백·Unicode 정규화는 중복 식별용 사본에만 적용한다. 같은 정규화 텍스트의 상충 레이블은 사전 등록한 정책으로 모두 제외하고 수를 기록한다. 원문은 유지한다.
- 문자 5-gram Jaccard 0.85 이상인 근접 중복은 같은 그룹으로 묶는다. 짧은 문장은 완전 중복으로만 묶는다. 대규모 후보 탐색은 고정 파라미터의 MinHash/LSH로 하고, 후보 쌍의 실제 Jaccard로 확정한다. 검출은 휴리스틱이므로 누출 부재의 수학적 증명이라고 부르지 않는다.
- 그룹을 나눈 뒤 레이블 층화로 개발 4,000건·선택 2,000건·최종 2,000건을 목표로 표본화한다. 각 클래스 1:1을 우선하되 중복 그룹을 깨서 숫자를 맞추지 않는다. 실제 그룹·행 수와 클래스 비율을 기록하고 부족하면 임의의 합성 문장으로 채우지 않는다.
- seed는 `20260905`로 고정한다. 최종 데이터는 개발 프로세스에서 원문·레이블·개별 예측을 출력하지 않는다. 사용자가 이미 보여준 문장, 도구 출력·출처 미리보기에서 노출된 문장과 그 중복 그룹은 최종 분할에서 제외한다.
- 데이터 manifest에 split별 ID·해시·그룹·생성 명령을 저장한다. 공유 파일시스템에서 접근 제한이 완전한 보안을 뜻하지는 않으므로 실행 로그와 열람 이력을 함께 남긴다.
- 최종 평가 전에 코드, 사전, 형태소 모델, 설정, 후보 선택 결과를 해시로 잠근다. 선택 분할에는 최대 3개 설정만 비교하고 모든 시도를 기록한다. 선택 분할의 사례를 보고 구현을 바꾸면 해당 분할도 개발 자료가 된다.
- 최종 평가 후 오류를 읽고 수정하는 것은 가능하지만, 그 순간 해당 세트는 다음 버전의 개발 자료다. 다음 버전의 독립 성능 주장은 새 외부 평가가 필요하다.
- 별점은 감성의 대리 정답이므로 레이블 잡음을 보고한다. 모델의 오답만 골라 정답을 고치지 않는다. 별도 사람 검수를 한다면 모델 예측을 보지 않은 검수자가 무작위 표본 전체를 검토하고 원래 지표와 별개로 보고한다. AI가 만든 레이블을 독립 사람 검수라고 부르지 않는다.

### 지표와 합격선

- 전체 Accuracy, positive/negative P/R/F1 및 그 평균 Macro F1, 2×3 혼동행렬을 계산한다. 분석 실패는 정답 클래스별 `analysis_error` 수를 별도로 붙이고 해당 클래스의 FN 및 전체 Accuracy 분모에 포함한다. 중립은 미매칭/점수 상쇄를 나누어 보고하며 어느 경우도 평가에서 제외하지 않는다.
- 최대 클래스만 예측한 정확도와 클래스별 고정 예측 기준선을 함께 기록한다. 현재 균형 세트에서는 50%지만 새 자료에서는 실제 비율로 계산한다.
- 표본 Accuracy의 Wilson 95% 구간과, 중복 그룹을 단위로 2,000회 재표집한 Accuracy/Macro F1 및 기준선 대비 차이의 95% 구간을 보고한다. Wilson은 행 독립 근사이며 그룹 bootstrap이 데이터 군집을 일부 반영한다. 알려지지 않은 사용자·상품 상관까지 해결했다고 주장하지 않는다.
- 비교는 같은 샘플에 대한 paired 비교로 한다. 단순 전후 퍼센트만 비교하지 않는다. 최종 주 비교 대상은 현재 작업 트리의 고정 기준선이며 나머지는 설명용 비교로 구분한다.
- **작업 목표:** 최종 분할 Accuracy ≥ 0.80, Macro F1 ≥ 0.80, 두 클래스 Recall 각각 ≥ 0.75, 그룹 bootstrap Accuracy 하한 ≥ 0.75, 현재 기준선 대비 Accuracy 차이의 95% 구간 하한 > 0.
- 0.80은 미션의 공식 합격선이나 이론적 보장치가 아니라 이번 작업의 사전 등록 목표다. 결과를 본 뒤 0.75 등으로 낮추지 않는다. 2,000건은 100건보다 불확실성을 줄이려는 설계이며, 군집 구조에 따라 유효 표본 수는 더 작다.
- 알려진 합성 200문항에 대한 92%/90% 유지는 최종 합격 조건이 아니다. 잘못된 예외를 제거하면서 떨어진 점수를 정당한 회귀 수정과 구분해 설명한다.

benchmark 원문과 원시 실행 산출물은 Git에 자동 추가하지 않는다. manifest 및 재현에 필요한 작은 집계 자료만 문서화하며 원본 사용·재배포 조건에 맞춘다.

타입·함수는 아래 경계를 기준으로 구현한다. 공용 결과 객체를 불필요하게 범용 엔진 인터페이스로 바꾸지 않는다.

```python
# models.py의 내부 타입. 기존 공개 결과 데이터 클래스와 구분한다.
@dataclass(frozen=True)
class MorphToken:
    lemma: str
    pos: str
    start: int
    end: int

@dataclass(frozen=True)
class SentimentEvent:
    term: str
    score: int
    token_start: int
    token_end: int
    lexicalized: bool  # 출처에서 확인한 비합성 관용구인지

# korean.py
def analyze_morphology(text: str) -> tuple[MorphToken, ...]: ...

# sentiment.py
def find_events(tokens: tuple[MorphToken, ...]) -> tuple[SentimentEvent, ...]: ...

# sentiment_rules.py
def score_events(
    text: str,
    tokens: tuple[MorphToken, ...],
    events: tuple[SentimentEvent, ...],
    *,
    apply_modifiers: bool,
) -> list[SentimentMatch]: ...
```

위 함수 본문 생략은 **인터페이스 표기**이며 구현이 완료되었다는 뜻이 아니다. 위치는 형태소 구간으로 관리하고 출력 raw는 원문에서 자른다. 수정어 연결 근거는 내부 추적 자료에 보관하여 잘못된 연결을 단위 테스트에서 검사한다.

- [ ] 아래 원문 계약을 실제 분석기로 검사한다. 형태소 lemma가 원문 부분 문자열과 항상 같다는 잘못된 가정은 하지 않는다.

```python
@pytest.mark.parametrize("text", [
    "🙂 친절했습니다", "좋다  좋다", "불편하지\t않았습니다",
    "햇빛을 피했다\n피해는 없다", "제품은 좋았어요.",
])
def test_morphology_source_ranges(text):
    tokens = analyze_morphology(text)
    assert tokens
    assert all(0 <= t.start < t.end <= len(text) for t in tokens)
    assert all(text[t.start:t.end].strip() for t in tokens)
```

- [ ] UTF-16 변환 테스트는 고정 문자 위치를 직접 기대값으로 둔다. 예: `🙂 좋다`에서 `좋`의 Python 시작 위치는 2다. 시작점·끝점의 surrogate 중간 위치를 정상 인덱스로 허용하지 않는다.
- [ ] 사용한 KOMORAN 모델 및 jar 해시를 기록한다. JVM 초기화·메모리 설정은 어댑터 한 곳에 두고 매 문장마다 초기화하지 않는다.

### Task 4 — 부정·강조의 국소 구문 합성

**Files:** 신규 `sentiment_rules.py`; 수정 `sentiment.py`, `models.py`, `tests/sentiment/test_modifiers.py`, `test_scoring.py`, `test_korean_matching.py`; 신규 `tests/sentiment/test_composition.py`.

**Consumes:** `MorphToken`, `SentimentEvent`. **Produces:** 기존 필드를 가진 `SentimentMatch` 목록과 동일 API의 `SentimentResult`.

- [ ] 4절의 문법별로 사건/연산자 연결과 소비 순서를 문서화한다. 처리 순서는 어휘 사건 확정 → 술어 그룹·절 경계 → 단일부정 → 명사화된 이중부정 → 강조 → 합산이다.
- [ ] 각 규칙을 추가하기 전에 서로 다른 감성 어휘를 넣은 긍정·부정 예와 적용하면 안 되는 반례를 만든다. 예문 생성 템플릿은 회귀용이며 최종 평가로 사용하지 않는다.
- [ ] 아래 테스트를 시작점으로 쓰고, 부정 횟수뿐 아니라 연결 대상까지 검증한다.

```python
def test_required_composition_contract():
    plain = analyze_sentiment("친절하다", apply_modifiers=False)
    negated = analyze_sentiment("친절하지 않다")
    doubled = analyze_sentiment("친절하지 않은 것은 아니다")
    emphatic = analyze_sentiment("매우 친절하다")
    assert plain.score > 0
    assert negated.score == -plain.score
    assert doubled.score == plain.score
    assert doubled.matches[0].negation_count == 2
    assert emphatic.score == 1.5 * plain.score
```

- [ ] 다른 절에 부정어를 삽입하는 반례, 내부 부정을 가진 관용구에 외부 부정을 추가하는 반례, 두 감성 사건 사이의 부정을 잘못 연결하는 반례를 추가한다.
- [ ] `apply_modifiers=False`는 동일한 사전·형태소·사건 분해를 쓰고 부정/강조 연산만 끈다. 비교 실험에서 매칭 방식까지 바꾸지 않는다.
- [ ] 기존 테스트 중 임의의 거리·타이브레이크를 정답으로 고정한 것은 새 문법 계약과 대조한다. 언어적 의미와 충돌하면 이유를 기록하고 의미 계약 테스트로 교체한다. 테스트 수를 유지하려고 잘못된 동작을 보존하지 않는다.
- [ ] `python -m pytest tests/sentiment -q`를 실행한다. 실패 원인을 형태소·사전·구문·합산으로 구분하고 각 단계의 실제 근거로 수정한다.

**Gate:** 핵심 문법의 정상·반례 및 수학적 불변식이 통과하고 문장별 if/lookup 보정이 없어야 한다.

### Task 5 — 개발 데이터에서 후보 선택과 원인 분리

**Files:** 신규 `scripts/evaluate_sentiment_benchmark.py`, `tests/test_benchmark_metrics.py`; 수정 `evaluation.py`; 기록 `docs/evaluation/sentiment-protocol.md`.

- [ ] 지표 테스트를 먼저 구현한다. 혼동행렬이 알려진 작은 데이터에서 Accuracy/F1/중립/분석 오류/기준선을 손계산 값과 비교한다. 그룹 bootstrap은 고정 seed, 모든 예측이 동일한 경우, 모델과 기준선이 같은 경우를 검증한다.

- [ ] 한 번에 한 요소를 바꾼 개발 실험을 수행한다: 고정 사전의 표면 매칭/형태소 매칭, 동일 매칭의 수정어 끔/켬, 기본 사전/도메인 추가, 이중부정 끔/켬. 총 개선을 개별 요인의 인과 효과로 과도하게 해석하지 않도록 상호작용도 기록한다.
