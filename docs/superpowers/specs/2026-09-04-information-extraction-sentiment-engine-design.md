# 정보 추출·감성 분석 엔진 설계 명세

- 상태: 설계 승인 완료, 구현 전
- 기준일: 2026-09-04
- 기준 문서: `docs/private/mission.md`, `docs/private/rubric.md`
- 대상 환경: Python 3.10 이상

## 1. 문서 목적과 기준

이 문서는 고객 문의와 같은 한국어 비정형 텍스트에서 정형 정보를 추출하고, 규칙 기반으로 전체 감성을 판정하는 프로젝트의 구현 기준을 정의한다.

`docs/private/mission.md`와 `docs/private/rubric.md`를 최상위 요구사항으로 삼는다. 이 명세와 두 기준 문서가 충돌하면 기준 문서가 우선한다. 보너스 과제는 구현 범위에서 제외한다.

## 2. 목표

시스템은 다음을 수행해야 한다.

1. 이메일, 전화번호, 날짜, 금액, URL을 정규표현식으로 추출한다.
2. 추출값을 유형별 표준 형식으로 정규화한다.
3. 200개 이상의 감성어 사전을 사용해 문장 점수를 계산한다.
4. 부정어, 강조어, 단일 이중부정 패턴을 점수에 반영한다.
5. Python 모듈 API와 CLI에서 동일한 분석 결과를 제공한다.
6. 정량 평가와 실패 사례 분석으로 규칙 기반 접근법의 성능과 한계를 설명한다.

## 4. 성공 기준

다음 조건을 모두 만족해야 프로젝트가 완료된 것으로 본다.

- 5개 추출 유형 각각에서 3가지 이상의 표기 변형을 처리한다.
- 유형별 10개 이상, 전체 50개 이상의 정보 추출 평가 문장을 제공한다.
- 감성 평가용 레이블 데이터 100개 이상을 제공한다.
- 감성어 사전에 200개 이상의 고유 표현을 포함한다.
- 감성 사전 안에 도메인 특화 표현 30개 이상을 별도로 식별한다.
- 정보 추출 유형별 Precision, Recall, F1을 산출한다.
- 감성 분석 Accuracy와 F1을 산출한다.
- 감성 기본 점수와 전체 규칙 적용 결과를 동일한 데이터에서 비교한다.
- 정보 추출 실패 사례 5건 이상과 감성 오분류 사례 10건 이상을 분석한다.
- 설치부터 CLI 실행, 테스트, 평가 재현까지 README만으로 수행할 수 있다.
- 모든 자동 테스트가 통과한다.

특정 성능 수치를 임의의 합격선으로 두지는 않는다. 이 과제의 필수 성공 기준은 평가 결과를 재현 가능하게 산출하고 오류 특성을 해석하는 것이다.

## 5. 시스템 구조

```text
입력 텍스트
  │
  ├─ ExtractionService
  │    ├─ 정규식 후보 탐색
  │    ├─ 유형별 유효성 검증
  │    └─ 유형별 정규화
  │
  └─ SentimentAnalyzer
       ├─ 토큰화
       ├─ 감성 표현 매칭
       ├─ 강조 범위 적용
       ├─ 부정/이중부정 범위 적용
       └─ 점수 및 레이블 판정
             │
             ├─ Python API
             ├─ CLI
             └─ Evaluator → 지표와 오류 사례
```

두 분석기는 독립적으로 사용할 수 있고, 통합 분석 함수가 두 결과를 하나로 조합한다. CLI는 별도 규칙을 구현하지 않고 공개 Python API만 호출한다.

## 6. 권장 파일 구조와 책임

```text
src/sentiment_engine/
├── __init__.py       # 공개 API 노출
├── models.py         # 공통 결과 타입
├── extraction.py     # 패턴, 후보 검증, 정규화, 추출 서비스
├── sentiment.py      # 토큰화, 사전 매칭, 수정 규칙, 점수 판정
├── evaluation.py     # 지표 계산과 평가 실행
└── cli.py            # 인자 처리와 출력 직렬화

data/
├── sentiment_lexicon.json
└── modifiers.json

tests/
├── extraction/
├── sentiment/
├── integration/
└── fixtures/

main.py
requirements.txt
README.md
```

- `models.py`는 결과 계약만 정의하며 분석 로직을 포함하지 않는다.
- `extraction.py`는 5개 유형의 패턴, 검증, 정규화를 유형별 함수로 구분한다.
- `sentiment.py`는 토큰화, 사전 조회, 수정어 범위 결정, 점수 집계를 내부 함수로 분리한다.
- `evaluation.py`는 예측 로직을 재구현하지 않고 분석기의 공개 API를 호출한다.
- 데이터 파일 수정만으로 감성어와 수정어를 추가할 수 있어야 한다.

현재 범위에서는 범용 규칙 엔진이나 플러그인 계층을 만들지 않는다.

## 7. 공개 인터페이스

### 7.1 Python API

```python
from sentiment_engine import analyze, analyze_sentiment, extract_information

extractions = extract_information(text)
sentiment = analyze_sentiment(text, apply_modifiers=True)
result = analyze(text)
```

계약은 다음과 같다.

- `extract_information(text: str) -> ExtractionResult`
- `analyze_sentiment(text: str, apply_modifiers: bool = True) -> SentimentResult`
- `analyze(text: str) -> AnalysisResult`
- 빈 문자열과 공백 문자열은 `ValueError`를 발생시킨다.
- 문자열이 아닌 입력은 `TypeError`를 발생시킨다.

`apply_modifiers=False`는 감성 사전 점수만 합산하여 규칙 적용 전후 평가에 사용한다.

### 7.2 CLI

최소 CLI 계약은 다음과 같다.

```bash
python main.py --text "문의는 support@example.com으로 주세요. 정말 좋지 않아요."
python main.py --text "..." --format json
python main.py --evaluate extraction
python main.py --evaluate sentiment
python main.py --evaluate all
```

- 기본 출력은 사람이 읽을 수 있는 텍스트 형식이다.
- `--format json`은 UTF-8 JSON을 출력한다.
- `--text`와 `--evaluate`는 동시에 사용할 수 없다.
- 잘못된 인자에는 설명이 포함된 오류 메시지와 0이 아닌 종료 코드를 반환한다.
- 정상 분석과 성공한 평가는 종료 코드 `0`을 반환한다.

## 8. 공통 결과 모델

### 8.1 추출 항목

각 추출 항목은 다음 필드를 가진다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `type` | 문자열 | `email`, `phone`, `date`, `money`, `url` 중 하나 |
| `raw` | 문자열 | 원문에서 매칭된 값 |
| `normalized` | 유형별 객체 또는 문자열 | 표준화된 값 |
| `start` | 정수 | 원문의 시작 문자 오프셋, 포함 |
| `end` | 정수 | 원문의 끝 문자 오프셋, 미포함 |

결과는 `start` 오름차순으로 정렬한다. 같은 유형과 같은 범위가 중복 매칭되면 검증을 통과한 가장 구체적인 후보 하나만 유지한다.

### 8.2 감성 결과

감성 결과는 다음 필드를 가진다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `score` | 실수 | 수정 규칙 적용 후 총점 |
| `label` | 문자열 | `positive`, `negative`, `neutral` 중 하나 |
| `mixed` | 불리언 | 양수와 음수 감성 기여가 모두 있었는지 여부 |
| `tokens` | 문자열 배열 | 분석에 사용한 토큰 |
| `matches` | 객체 배열 | 감성어와 수정어별 점수 계산 과정 |

점수는 출력 시 소수점 불안정을 피하도록 합산 완료 후 소수 여섯째 자리에서 반올림한다.

### 8.3 통합 결과

`AnalysisResult`는 입력 원문, 유형별 추출 목록, 감성 결과, 진단 정보를 포함한다. 진단 정보는 제외된 정규식 후보와 제외 사유를 담되 정상적인 미매칭은 오류로 기록하지 않는다.

## 9. 정보 추출 요구사항

모든 정규표현식은 Python 내장 `re` 모듈로 구현한다. 각 패턴 바로 위에 의도, 지원 형식, 주요 그룹, 문자 클래스, 수량자, 알려진 경계를 설명하는 주석을 둔다.

정규식은 후보를 찾는 역할만 한다. 의미적 유효성은 별도 검증 함수가 판단한다.

### 9.1 이메일

최소 지원 변형:

- `user@domain.com`
- `user.name@sub.domain.co.kr`
- `user+tag@example.org`

정규화:

- 원문 로컬 파트는 보존한다.
- 도메인은 소문자로 변환한다.
- 결과 형식은 문자열이다.

검증 경계:

- 로컬 파트와 도메인이 비어 있으면 제외한다.
- 도메인에 점으로 구분된 유효 레이블과 최종 도메인이 있어야 한다.
- 완전한 RFC 5322 구현은 범위 밖이다.

### 9.2 전화번호

최소 지원 변형:

- `010-1234-5678`
- `010 1234 5678`
- `01012345678`
- `02-123-4567`
- `031-1234-5678`

정규화:

- 구분자를 제거한 뒤 번호 구조에 맞춰 하이픈을 다시 삽입한다.
- 결과 형식은 문자열이다.

검증 경계:

- 이동전화 `010`과 지역번호 `02`, `031`, `032`, `033`, `041`, `042`, `043`, `044`, `051`, `052`, `053`, `054`, `055`, `061`, `062`, `063`, `064`를 지원한다.
- 국번은 3자리 또는 4자리, 가입자 번호는 4자리로 제한한다.
- 자릿수가 형식에 맞지 않으면 제외한다.
- 국제전화와 한글 숫자 표기는 범위 밖이다.

### 9.3 날짜

최소 지원 변형:

- `2024년 1월 15일`
- `2024/01/15`
- `2024-01-15`

정규화:

- 실제 달력 날짜인지 검증한다.
- 결과는 ISO 8601 날짜 문자열 `YYYY-MM-DD`이다.

검증 경계:

- 윤년을 포함한 달력 검증을 수행한다.
- 연·월·일이 모두 있는 날짜만 지원한다.
- `2024-02-30`과 같은 값은 진단 사유와 함께 제외한다.

### 9.4 금액

최소 지원 변형:

- `10,000원`
- `12000원`
- `1억 2천만원`
- `$100`

정규화 결과는 다음 객체다.

```json
{"amount": 120000000, "currency": "KRW"}
```

- 원화 단위 `억`, `천만`, `만`, `천`을 정수 원 단위로 환산한다.
- 쉼표를 제거하고 정수로 변환한다.
- `$`는 `USD`, `원`은 `KRW`로 기록한다.
- 소수 금액, 환율 변환, 통화 기호가 없는 일반 숫자는 범위 밖이다.
- 단위가 중복되거나 큰 단위부터 작은 단위 순서를 위반한 표현은 제외한다.

### 9.5 URL

최소 지원 변형:

- `https://www.example.com`
- `http://example.com/path`
- `https://www.example.com/path?query=value`

정규화:

- 스킴과 호스트를 소문자로 변환한다.
- 경로, 쿼리, 프래그먼트의 대소문자와 인코딩은 보존한다.
- 결과 형식은 문자열이다.

검증 경계:

- `http`와 `https`만 지원한다.
- 호스트가 없으면 제외한다.
- 문장 종결 기호와 감싸는 괄호·꺾쇠는 URL에 포함하지 않는다.

## 10. 감성 분석 요구사항

### 10.1 사전

`data/sentiment_lexicon.json`은 프로젝트에서 직접 선별·구축해 저장소에 포함하는 항목 객체의 JSON 배열이며 최소 200개의 고유 `term`을 가진다. 외부 감성 자료는 항목 선정의 참고 자료로 사용할 수 있지만, 실행 시 외부 사전을 내려받는 구조에는 의존하지 않는다. 각 항목은 다음 정보를 포함한다.

```json
{
  "term": "만족",
  "variants": ["만족해요", "만족했다"],
  "score": 2,
  "domain": "customer_support",
  "source": "project"
}
```

- 감성 점수는 `-3`부터 `3`까지의 0이 아닌 정수다.
- `variants`는 해당 감성어로 처리할 표면형 문자열 배열이며, 등록 변형이 없으면 빈 배열을 사용한다. 변형은 200개 기준에 별도 단어로 합산하지 않는다.
- `±1`은 약한 감성, `±2`는 명확한 감성, `±3`은 매우 강한 감성이다.
- 도메인 특화 단어 30개 이상은 `domain` 필드로 구분한다.
- 직접 구축한 항목과 외부 자료에서 참고한 항목의 출처를 기록한다.
- 외부 사전을 사용하면 README에 사전명, 원본 위치, 라이선스, 가공 방법을 명시한다.

`data/modifiers.json`은 부정어와 강조어를 분리해 다음 스키마로 관리한다.

```json
{
  "negations": [
    {"term": "않다", "variants": ["않아", "않은", "않았어요"]}
  ],
  "emphasizers": [
    {"term": "정말", "variants": [], "multiplier": 1.5}
  ]
}
```

### 10.2 토큰화와 표현 매칭

- 유니코드 한국어·영문·숫자 토큰과 문장부호 경계를 구분하는 자체 경량 토크나이저를 사용한다.
- 공백 기반 어절을 기본 단위로 유지하면서 흔한 조사·어미가 붙은 사전 표현을 매칭할 수 있도록 표면형과 등록 변형을 사용한다.
- 여러 단어로 된 사전 표현은 가장 긴 표현부터 매칭한다.
- 같은 토큰 범위는 하나의 감성 표현에만 배정한다.
- 형태소 분석기 수준의 일반화는 목표가 아니며 지원 변형은 사전과 테스트로 명시한다.

### 10.3 기본 점수

기본 점수는 매칭된 감성 표현 점수의 합이다.

```text
base_score = Σ lexicon_score(match)
```

`apply_modifiers=False`이면 이 점수를 그대로 최종 점수로 사용한다.

### 10.4 강조어

- 강조어는 같은 문장부호 구간에서 바로 다음에 매칭되는 감성 표현 하나에 적용한다.
- 감성 표현과 강조어 사이에는 최대 2개 토큰만 허용한다.
- 기본 강조 배수는 `1.5`이며 표현별 배수를 데이터에서 지정할 수 있다.
- 여러 강조어가 같은 감성 표현에 적용되면 배수를 곱하되 최종 배수는 `2.0`으로 제한한다.

예: `정말 만족`은 `만족(+2) × 1.5 = +3`이다.

### 10.5 부정어와 이중부정

- 부정어는 같은 문장부호 구간의 감성 표현 전후 2개 토큰 안에서만 영향을 준다.
- 하나의 부정어가 여러 감성 표현에 중복 적용되지 않도록 가장 가까운 감성 표현에 연결한다.
- 연결된 부정 표현 개수가 홀수면 감성 점수의 부호를 반전한다.
- 연결된 부정 표현 개수가 짝수면 원래 부호를 유지한다.
- 이 정책은 단일 감성 표현 주변의 명시적 이중부정만 처리한다.

예:

- `좋지 않다`: `+2 × -1 = -2`
- `좋지 않은 것은 아니다`: 두 부정 표현을 인식한 경우 `+2 × (-1)^2 = +2`

문장 전체 논리, 반어, 부정의 초점 해석은 범위 밖이며 실패 사례로 분석한다.

### 10.6 규칙 적용 순서

개별 감성 표현의 기여 점수는 다음 순서로 계산한다.

1. 사전 기본 점수를 조회한다.
2. 연결된 강조어 배수를 적용한다.
3. 연결된 부정어 개수의 홀짝에 따라 부호를 결정한다.
4. 모든 감성 표현의 기여 점수를 합산한다.

```text
contribution = lexicon_score × emphasis_multiplier × (-1)^negation_count
final_score = Σ contribution
```

### 10.7 레이블과 복합 감성

- `score > 0`: `positive`
- `score < 0`: `negative`
- `score == 0`: `neutral`
- 수정 후 기여 점수 중 양수와 음수가 모두 존재하면 `mixed=true`다.

`mixed`는 진단 속성이며 최종 레이블을 대체하지 않는다. 양수와 음수가 상쇄되어 0이면 `neutral`, 그 외에는 합산 점수의 부호에 따른다. Aspect별 감성 판정은 하지 않는다.

## 11. 오류와 경계 처리

- 비문자열 API 입력은 즉시 `TypeError`, 빈 문자열과 공백 문자열은 `ValueError`로 거부한다.
- 정규식 후보 하나의 검증·정규화 실패는 전체 분석을 중단시키지 않는다.
- 제외한 후보는 유형, 원문, 위치, 사유 코드를 진단 정보에 기록한다.
- 데이터 파일이 없거나 JSON 스키마가 잘못되었거나 감성어가 200개 미만이면 시작 단계에서 명시적 설정 오류를 발생시킨다.
- 감성어 중복, 0점 또는 범위 밖 점수, 유효하지 않은 강조 배수는 설정 오류로 처리한다.
- CLI는 사용자 입력 오류와 내부 설정 오류를 구분해 stderr에 출력한다.
- 정상 입력에서 추출 항목이나 감성 단어가 없는 상태는 오류가 아니다.

진단 사유 코드는 테스트에서 안정적으로 검증할 수 있는 짧은 문자열로 정의한다. 예: `invalid_calendar_date`, `invalid_phone_length`, `missing_url_host`.

## 12. 평가 설계

### 12.1 정보 추출 데이터

- 직접 작성한 문장 50개 이상을 사용한다.
- 각 추출 유형의 정답 항목이 등장하는 문장을 최소 10개 포함한다.
- 각 유형마다 지원 표기 변형을 최소 3가지 포함한다.
- 한 문장에 여러 유형 또는 같은 유형의 여러 항목이 나타나는 사례를 포함한다.
- 거짓 양성 검증을 위해 이메일처럼 보이는 일반 문자열, 잘못된 날짜, 통화가 아닌 숫자 등의 음성 사례를 포함한다.

정답은 문장 ID, 유형, `raw`, `normalized`, `start`, `end`를 가진다.

### 12.2 정보 추출 지표

예측과 정답은 문장 ID, 유형, 문자 범위, 정규화값이 모두 같을 때 정확히 일치한 것으로 본다.

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2 × Precision × Recall / (Precision + Recall)
```

- 유형별 지표와 전체 micro 평균을 보고한다.
- 분모가 0이면 해당 지표는 `0.0`으로 기록하고 평가 보고서에 이유를 남긴다.
- Precision은 잘못 추출한 항목의 정도, Recall은 놓친 정답 항목의 정도로 해석한다.

### 12.3 감성 데이터와 지표

- 사람이 부여한 레이블이 있는 한국어 문장 100개 이상을 사용한다.
- 평가 레이블은 `positive`, `negative`를 기본으로 하며, 자체 데이터에 `neutral`이 있으면 별도 클래스 지표도 보고한다.
- 데이터 출처, 라이선스, 샘플링 또는 자체 작성 방법을 README에 기록한다.
- 같은 데이터에 `apply_modifiers=False`와 `True`를 각각 실행한다.

보고 지표:

- 전체 Accuracy
- 클래스별 Precision, Recall, F1
- macro F1
- 이진 데이터인 경우 positive 클래스 F1
- 규칙 적용 전후 지표 차이

이진 정답 데이터에서 `neutral` 예측은 오분류로 계산한다.

### 12.4 실패 사례 분석

정보 추출 실패 사례 5건 이상을 다음 항목으로 기록한다.

- 입력과 정답
- 실제 출력
- 실패 유형: FP, FN, 정규화 오류
- 원인: 패턴 범위, 후보 검증, 지원하지 않는 표현 등
- 정밀도 또는 재현율에 미친 영향
- 개선 방향과 예상 부작용

감성 오분류 사례 10건 이상도 같은 구조로 기록하며, 원인은 토큰화, 사전 누락, 부정 범위, 강조 범위, 복합 감성, 문맥·반어 등으로 분류한다.

## 18. 승인된 설계 결정

- 보너스 과제는 수행하지 않는다.
- Python 모듈 API와 CLI를 함께 제공한다.
- 범용 규칙 엔진 대신 경량 모듈형 구조를 사용한다.

- 두 기준 문서의 필수 항목은 이 명세의 요구사항 추적표와 테스트로 연결한다.
